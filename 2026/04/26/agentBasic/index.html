agent相关概念

智能体（Agent）概念

Agent 可以理解为一种“能自己推进任务的 AI 结构”。它不只是回答问题，而是会先理解目标、再拆解步骤、调用工具、读取上下文、根据结果继续推进，直到把一个任务尽量完整地做完。

如果把普通对话模型看成“问一句答一句”，那 agent 更像“带执行能力的助手”。它通常会围绕一个目标反复进行：

  1. 理解任务
  2. 规划步骤
  3. 获取上下文
  4. 调用工具
  5. 观察结果
  6. 调整下一步动作

总结构

如果把这篇文章里的概念放到一张图里，可以大致理解成：

  • Agent：总的执行体，负责完成任务
  • Prompt：告诉 Agent 怎么说、怎么思考、怎么输出
  • Context：告诉 Agent 现在看到了什么、还缺什么信息
  • Workflow：告诉 Agent 先做什么、后做什么、什么时候停下来确认
  • Harness：给 Agent 提供稳定的运行环境、配置和验证方式
  • MCP：让 Agent 接入外部工具和上下文的协议
  • Skill：让 Agent 具备特定任务能力的模块
  • RAG：让 Agent 从外部知识库里检索信息的增强方式
  • subAgent：把大任务拆成多个更小的执行单元

这个顺序也基本对应了“从上到下”的关系：Agent 是主体，Prompt / Context / Workflow / Harness 是工程层，MCP / Skill / RAG / subAgent 是让 Agent 更能干活的补充能力。

Agent 的结构

一个比较完整的 agent，通常会包含下面这些部分：

  • 模型：负责推理、生成和决策
  • Prompt / 规则：告诉 agent 应该怎么工作，输出什么格式，遵守什么边界
  • Context：提供任务相关信息、仓库约定、历史对话和外部资料
  • Tools：让 agent 可以真正做事，比如读写文件、查接口、跑测试、发请求
  • Memory：保存长期记忆或阶段性结论，减少重复解释
  • Planner / Workflow：把任务拆成步骤，控制执行顺序
  • Verifier：检查结果是否正确，比如 lint、test、review

从工程角度看，agent 的关键不是“会不会说”，而是“能不能稳定做完事”。所以真正可用的 agent，往往不是单靠模型能力，而是靠 prompt、context、tool、workflow、验证环节一起配合。

subAgent

subAgent 可以理解为“被主 Agent 调度的子执行单元”。主 Agent 负责理解总目标、拆解任务和整合结果，subAgent 负责在一个更小、更明确的范围内完成具体工作。

作用

  • 把复杂任务拆成多个可以独立执行的小任务
  • 让不同子任务并行推进，提高效率
  • 让每个子任务只关注局部上下文，降低干扰
  • 让不同子 Agent 承担不同角色，比如规划、编码、测试、review

结构

一个常见的 subAgent 结构通常是：

  • 主 Agent：负责总控、分发任务、整合结果
  • subAgent：负责执行具体子任务
  • 边界约束：明确 subAgent 能做什么、不能做什么
  • 输入输出契约：规定 subAgent 需要返回什么结果

什么时候需要 subAgent

  • 任务天然可以拆分成多个互不冲突的部分
  • 需要并行处理多个文件、多个模块或多个分支
  • 一个 Agent 同时处理太多上下文，容易跑偏
  • 需要把“计划、实现、测试、复核”分给不同角色
  • 需要让子任务只看到局部上下文，避免污染主任务

什么时候不需要

  • 任务很小，单个 Agent 就能快速完成
  • 子任务之间强耦合，拆开反而会增加协调成本
  • 结果必须在一个极短链路内完成，来不及分发
  • 没有清晰的任务边界，拆分后容易产生重复工作

使用建议

  • 给 subAgent 一个非常明确的目标
  • 控制它能访问的上下文，不要一次性塞太多信息
  • 让它返回结构化结果，方便主 Agent 汇总
  • 子任务结束后尽快回收，不要无限扩散
  • 对于需要验证的步骤，让 subAgent 直接输出可检查的证据，比如命令、diff 或测试结果

现在常见的搭建方法

1. 纯 prompt 驱动

这是最轻量的方式。直接在 prompt 里定义角色、步骤和输出格式，让模型按固定流程工作。

  • 优点：上手快、成本低
  • 缺点：复杂任务容易跑偏，稳定性一般

2. Prompt + Context 驱动

在 prompt 之外，再补充项目文档、规则文件、历史结论和任务上下文，让 agent 有更多可依赖的信息。

  • 适合仓库型任务
  • 适合需要遵守团队规范的场景
  • 这也是 prompt工程 和 context工程 经常一起出现的原因

3. Workflow 驱动

通过固定流程把任务拆开，比如先澄清需求，再出方案，再实现，再验证。

  • 适合复杂任务
  • 能减少一步到位带来的失控
  • superpowers、openspec 这类东西本质上都在强化 workflow

4. Harness 驱动

把 agent 放到一个可控的工程环境里，提供统一的配置、上下文、权限、工具和验证方式。

  • 适合团队协作
  • 适合持续迭代
  • 方便验证配置是否真的生效

5. 工具协议驱动

通过 MCP 之类的协议，把外部工具、数据源和上下文接进来，让 agent 能扩展到代码仓库、文档系统、自动化流程里。

  • 适合需要连接真实系统的场景
  • 让 agent 从“会说”变成“能做”

怎么理解这几层关系

  • prompt 决定 agent 怎么说
  • context 决定 agent 看什么
  • workflow 决定 agent 怎么做
  • harness 决定 agent 在什么环境里做
  • tools / MCP 决定 agent 能实际做什么

所以一个成熟的 agent，通常不是单点能力，而是一整套工程化组合。

AI编码应用

现在市面上的 AI 编码应用，大体可以分成两类：一类是集成在 IDE 里的，一类是运行在终端里的 CLI 工具。它们的共同点是都不只是“聊天”，而是会读取项目上下文、遵守仓库约定，并尽量按工程化方式完成代码修改、解释和验证。

IDE 类

GitHub Copilot

  • 常见于 VS Code、JetBrains、Visual Studio、Xcode 等 IDE
  • 主要通过仓库级说明文件、路径级说明文件和 agent 文件来约束行为
  • 常见约束方式包括：
    • .github/copilot-instructions.md 作为仓库级说明
    • .github/instructions/*.instructions.md 作为路径级说明
    • AGENTS.md、CLAUDE.md、GEMINI.md 作为 agent 指令文件
  • 适合团队代码规范比较明确、希望把约束写进仓库里的场景

Cursor

  • 属于 AI 原生 IDE，常用于代码编辑、重构和对话式改动
  • 常见约束方式包括：
    • .cursor/rules 下的 Project Rules
    • User Rules 作为全局规则
    • AGENTS.md 作为仓库级 agent 指令
    • 旧的 .cursorrules 仍支持，但已经偏 legacy
  • 适合希望把规则和编辑体验深度绑定的场景

Windsurf

  • 也是偏 agent 化的 AI IDE
  • 常见约束方式包括：
    • AGENTS.md，会按目录自动生效
    • .windsurf/rules 下的 Rules
    • Memories 用来保留对话和项目上下文
    • 通过不同 trigger 模式控制规则何时生效
  • 适合希望把规则、记忆和工作区上下文统一管理的场景

CLI 类

Claude Code

  • 运行在终端里，更适合和仓库、脚本、测试命令一起工作
  • 常见约束方式包括：
    • ./CLAUDE.md 作为项目共享记忆
    • ~/.claude/CLAUDE.md 作为个人全局记忆
    • .claude/settings.json 和 .claude/settings.local.json 管权限、环境变量和工具行为
    • permissions.deny 用来禁止读取敏感文件
    • MCP servers 用来扩展工具能力
  • 适合需要强上下文、强权限控制、强工具集成的场景

OpenAI Codex CLI

  • 也是偏终端使用的编码代理
  • 常见约束方式包括：
    • 仓库中的 AGENTS.md 作为主要项目指令
    • ~/.codex/config.toml 作为用户级配置
    • config.toml 里的特性开关和项目相关设置控制行为
  • 适合把编码、测试、审查流程放到命令行里自动推进的场景

GitHub Copilot CLI

  • 适合在终端里做局部代码修改、重构和解释
  • 约束方式和 Copilot IDE 比较接近：
    • 仓库级 .github/copilot-instructions.md
    • 路径级 .github/instructions/*.instructions.md
    • AGENTS.md 作为 agent 指令文件
  • 适合已经在 Copilot 体系里，希望把终端也纳入统一规则的团队

它们怎么约束规范

这些工具约束规范的方式，本质上可以分成几层：

  • 仓库级规则：把编码规范、目录约定、测试命令写进仓库
  • 路径级规则：不同目录使用不同规范，避免一份大文档写到底
  • 用户级规则：个人偏好、默认行为、常用命令
  • 权限控制：限制敏感文件、危险命令和外部访问
  • 上下文控制：让工具只看和当前任务相关的文件
  • 工作流控制：通过 workflow、skills、rules、memory 让它按固定流程走

简单理解，IDE 更强调“编辑时的实时约束”，CLI 更强调“终端里的流程化执行”；而真正让它们稳定的，通常不是模型本身，而是仓库规则、权限、上下文和工作流一起配合。

辨析：credits 和 token

credits 和 token 也不是一回事，不能直接画等号。

  • token 是模型侧的计量单位，通常表示输入和输出文本被切分后的单位
  • credits 是平台侧的计费或额度单位，通常表示你还能用多少服务、请求或费用额度

更直白一点说：

  • token 关注的是“模型到底处理了多少文本”
  • credits 关注的是“你这个账户还能消费多少资源”

所以它们通常处在不同层级：

  • token 影响模型上下文长度、输入输出成本、响应限制
  • credits 影响平台配额、账单、订阅额度或请求次数

不同产品对 credits 的定义也不一样。有的产品把 credits 当作统一的消费单位，有的产品把它映射成 request、premium request 或某种内部计费额度。相比之下，token 的定义更偏模型通用概念，尤其在 OpenAI 这类 API 里，价格通常直接按 token 计算。

所以实际使用时要分开看：

  • 看到 token，先想模型输入输出和上下文长度
  • 看到 credits，先想平台额度、订阅和账单规则
  • 不要默认 1 credit = 1 token，这个换算一般并不存在固定标准

RAG

Retrieval-Augmented Generation (RAG) 检索增强生成是一种AI技术，通过检索外部知识库中的相关信息来增强语言模型的生成能力。它结合了检索系统和生成模型，能够提供更准确、基于事实的响应，避免生成幻觉内容。一般流程为：
query 向量化 -> 向量相似度检索 -> 文档放入 prompt ->大模型生成回答
必要时可以让大模型参与 RAG 的流程，自己做 query 重写，效果评估，让大模型自主决策搜什么、效果怎么样，要不要重新搜。

缺点

  1. 忽视文档结构。经典RAG将文档机械地切成独立片段，丢失了章节层次和上下文连贯性。如果答案涉及多个段落关联或跨章节的信息，简单的相似度检索往往顾及不到。将长文档硬切会破坏其自然逻辑flow，导致模型生成时缺乏重要上下文。
  2. 检索精度依赖嵌入质量。当向量匹配失灵时，调试问题常变成噩梦——究竟是嵌入向量没表示出关键细节？语义空间偏差？还是索引过期未包含最新内容？。向量检索有时匹配的是大致相关的段落，却未必包含问题所需的具体事实。相反，传统关键字搜索（如grep）行为简单可预期：搜索不到某关键词，就说明文档里没有，这种确定性在诊断检索问题时非常宝贵。
  3. 段落截断与顺序问题。也会影响效果。RAG常按固定长度截断文本，可能把紧密关联的信息分散在不同片段中，导致检索返回的碎片各自孤立，模型难以拼凑完整答。而当检索返回多个片段时，如何排序放入Prompt也有讲究。如果关键内容被排在中间，模型注意力可能不足，出现“中段遗失”现象，大幅降低答案准确率。
  4. 成本与隐私问题：定期嵌入新数据、监控向量库性能都增加复杂度；向量可能泄露原文信息，需要防范embedding反推原文的风险。

MCP

Model Context Protocol (MCP) 是一种协议，用于定义AI模型如何与上下文数据和工具交互。它可能涉及工具调用、上下文传递和状态管理，帮助模型更好地理解和处理复杂任务。

辨析：MCP 和 tool calling / function calling

MCP 和 tool calling / function calling 不是同一层的东西，所以也不能简单理解成“谁取代了谁”。

  • tool calling / function calling 更像是模型或 API 的能力：模型在对话中决定调用某个工具，应用层再根据这个调用去执行函数或外部动作
  • MCP 更像是连接层协议：它定义了客户端、服务器、工具、资源、上下文该怎么标准化地对接

所以更准确的理解是：

  • function calling 解决“模型如何请求工具”
  • MCP 解决“工具和上下文如何标准化暴露给模型和应用”

它们的关系更像是可以组合，而不是互相完全替代。实际工程里常见的做法是：

  • 底层工具仍然通过函数调用或类似机制触发
  • 上层把这些工具包装成 MCP server
  • agent/client 再通过 MCP 统一发现、连接和使用这些能力

也就是说，MCP 不是把 function calling 消灭掉，而是给工具接入和上下文分发提供了一套更标准的协议。很多场景里，MCP 反而会建立在已有的 tool calling 能力之上。

MCP的安装

vscode

  1. 打开VS Code。
  2. 使用命令面板（快捷键 Cmd + Shift + P）搜索并选择 “MCP: Add server…”。
  3. 选择添加方式：可以从MCP Marketplace添加服务器，或手动配置HTTP服务器。
  4. 如果添加本地服务器，提供服务器URL（例如 http://localhost:3000），并为服务器命名。
  5. 系统会提示同意权限对话框，授予必要的访问权限（如 mcp:tools）。
  6. 配置完成后，服务器的工具将在VS Code中可用，可以通过聊天视图使用 # 符号调用。

cursor

Cursor 基于 VS Code，因此安装流程类似：

  1. 打开 Cursor。
  2. 使用命令面板（快捷键 Cmd + Shift + P）搜索并选择 “MCP: Add server…”。
  3. 按照与 VS Code 相同的步骤添加服务器：从市场添加或手动配置。
  4. 对于本地服务器，提供URL并同意权限对话框。
  5. 配置后，可以在 Cursor 中使用 MCP 工具进行交互。

Skill

Skill 在AI代理系统中指的是一种模块化的能力或功能模块，允许代理执行特定任务，如代码生成、搜索、编辑等。技能可以是预定义的、可扩展的，并通过协议如MCP进行调用。简单理解skill相当于一个固化的prompt，目前仓库里的skill是大家认为可以稳定被调用、有效执行的prompt。当然什么时候调用还是由模型决定

prompt工程

如果从 AI 工程的视角来看，prompt工程和 harness 工程、context 工程可以算是同一层级的概念，只是关注点不同。prompt工程更关注“怎么把问题问清楚、怎么让模型按预期输出”，核心是设计好提示词、约束词和输出格式。

作用

  • 明确任务目标，减少模型自由发挥
  • 规定输出结构，让结果更稳定
  • 通过角色、格式、示例分别约束不同维度
  • 让同一个模型在不同场景下表现更一致

常见做法

  • 先说明背景，再说任务，再给约束
  • 让系统规则、角色设定和示例各自承担不同职责
  • 对复杂任务拆成分步 prompt
  • 对敏感任务增加反例和边界条件

适合场景

  • 需要模型按固定格式返回内容
  • 需要减少幻觉和跑题
  • 需要把一次性任务流程化

System prompt 设计

System prompt 可以理解为“最高优先级的行为说明”。它通常用来定义模型的角色、边界、输出风格和执行原则，告诉模型“你是谁、你要遵守什么、你不能做什么”。

设计重点

  • 先定义角色，再定义任务
  • 明确优先级，避免后续指令和系统规则冲突
  • 约束输出风格、格式和语气
  • 写清楚禁区，比如不要编造、不要越权、不要输出敏感信息
  • 把最关键的规则放在前面，避免被长上下文冲淡

常见写法

  • 角色定义：你是一个资深前端工程助手
  • 行为约束：回答必须基于已有上下文，不确定时要先说明不确定
  • 输出格式：先结论，后步骤，最后给代码
  • 安全约束：不要泄露密钥，不要执行危险命令

适合场景

  • 需要固定模型的人设和行为风格
  • 需要统一多个任务的输出格式
  • 需要给 agent 一个长期稳定的底层规则

Few-shot 示例

Few-shot 示例就是在 prompt 里给模型少量高质量样例，让它通过“看例子”学会你想要的输出风格和处理方式。

设计重点

  • 示例要短，但要典型
  • 正例和反例要区分清楚
  • 示例最好和真实任务高度相似
  • 不要放太多例子，避免喧宾夺主
  • 示例里的输入输出格式要稳定一致

常见写法

  • 输入：给出一段需求描述
  • 输出：给出你期望的最终结果
  • 可以用 1 到 3 组样例让模型学习

适合场景

  • 需要固定输出结构
  • 需要模型学习特定判断标准
  • 需要处理容易歧义的任务

CoT 思维链设计 (Chain of Thought)

CoT 思维链是一种引导模型展示中间推理步骤的技术。它通过让模型在给出最终答案之前，先显式地写出推理过程（“思维链”），从而显著提高其处理复杂逻辑、数学计算或多步任务的准确性。

设计重点

  • 显式引导：在 Prompt 中明确要求模型“逐步思考（think step by step）”。
  • 展示逻辑：要求模型不仅给出结果，还要解释其推理背后的逻辑或决策依据。
  • 结构化推理：引导模型使用特定的标识符（如 Thought:）来记录中间思考过程。

常见写法

  • “请一步步分析这个问题，并在给出最终答案前说明你的思路。”
  • “在执行任何操作之前，请先通过思考块（Thought block）列出你的计划。”
  • “Let’s think step by step to ensure we cover all requirements.”

适合场景

  • 逻辑复杂的编码任务（如算法实现、重构建议）。
  • 需要高透明度和可解释性的决策场景。
  • 任务涉及多个前置条件或需要权衡多个方案的情况。

context工程

context工程更关注“把哪些信息喂给模型、以什么顺序喂、哪些信息应该长期保存”。如果说 prompt工程解决的是“怎么问”，那 context工程更像是在解决“让模型看到什么、看多少、先看什么”。

作用

  • 控制上下文长度，避免无关信息过多
  • 提供任务所需的关键事实、文件和约定
  • 通过层级上下文让模型先看全局，再看局部
  • 把长期规则和短期任务分开管理

常见做法

  • 用仓库文件提供长期上下文，比如 AGENTS.md、CLAUDE.md
  • 用分层目录或就近规则控制上下文优先级
  • 只给和当前任务相关的文件，而不是一次性塞全部内容
  • 对长对话做总结，保留关键结论
  • 把可复用知识沉淀成 docs、spec 或 notes

适合场景

  • 仓库内容较多，需要控制输入范围
  • 多轮对话中需要保留历史结论
  • 任务依赖项目约定、接口定义、业务背景

harness工程

harness 工程可以理解成一个“最小验证仓库”或者“测试沙盒”，它的目标不是承载真实业务，而是专门用来验证 AI 编码工具是否真的读到了仓库约定、权限配置、工具配置和测试命令。参考 OpenAI 提到的 harness engineering 思路，AGENTS.md 更适合做导航和约束，而不是把所有知识都堆进去。

常见配置

Codex

  • 仓库根目录放 AGENTS.md，写清楚代码风格、目录结构、测试命令、禁止修改范围
  • 如果需要配置 MCP 或全局行为，可以放到 ~/.codex/config.toml
  • 分层规则可以继续往子目录里放更具体的 AGENTS.md，子目录优先级更高

GitHub Copilot

  • 仓库级说明通常放在 .github/copilot-instructions.md
  • 路径级说明可以放在 .github/instructions/*.instructions.md
  • 面向 agent 的约束也可以放 AGENTS.md，Copilot 会优先读取离当前文件更近的那一层
  • 如果项目还希望兼容其他 agent，根目录的 CLAUDE.md 或 GEMINI.md 也可以一起配合使用

Claude Code

  • 项目共享记忆放在 ./CLAUDE.md
  • 个人全局记忆放在 ~/.claude/CLAUDE.md
  • 项目级设置放在 .claude/settings.json
  • 个人项目临时设置放在 .claude/settings.local.json
  • 如果需要引入更多上下文，可以在 CLAUDE.md 里用 @path/to/file 的方式导入

怎么验证有效性

  • 先放一条独特的测试指令，比如要求工具回答时先输出一个固定口令
  • 用最简单的任务去试探它，比如让工具总结仓库规则、生成一个小改动、或者说明测试命令
  • Codex 可以通过让它复述 AGENTS.md 里的约定，或者做一个违反约定的测试来确认是否真的拦住了
  • Copilot 可以看 Chat 或 Inline Chat 的 References 列表，确认 .github/copilot-instructions.md 是否被引用
  • Claude Code 可以用 /memory 查看当前会话到底加载了哪些 CLAUDE.md
  • 再补一个子目录覆盖规则，验证是否真的按“就近优先”生效
  • 最后跑一遍仓库里最小的 lint 或 test 命令，确认这些配置不仅被读取了，而且会影响实际执行

workflow

workflow 可以理解为 AI 工程里的“执行流程设计”。它关心的不是某个模型有多强，而是模型在接任务时，应该先想什么、后做什么、在哪里确认、什么时候停下来让人检查。好的 workflow 往往会把需求确认、方案设计、实现、验证这几步串起来，减少模型直接写代码带来的发散和返工。

superpowers

superpowers 更像是一个面向 coding agent 的方法论加技能框架。它把开发过程拆成更稳定的步骤，让 agent 不要一上来就写代码，而是先澄清目标、再形成 spec、再给出计划，最后再进入实现和复核。

功能

  • 引导 agent 先问清楚问题，再开始动手
  • 把需求整理成可阅读的 spec
  • 输出可执行的实现计划
  • 借助子 agent 和自动触发的 skills 执行拆解后的任务
  • 强调 TDD、review 和逐步推进，减少一次性大改

使用方式

superpowers 通常是以插件或 marketplace 的方式安装到不同 harness 里使用。比如在 Claude Code、Codex、Cursor 这类工具里，安装对应插件后，agent 就会开始遵循它的流程。

一个典型使用方式是：

  1. 先让 agent 进入需求澄清阶段
  2. 再让它输出设计或 spec
  3. 确认设计后开始执行任务
  4. 最后检查测试、review 和收尾

适合场景

  • 需求比较模糊，需要先对齐目标
  • 想让 AI 先出方案再写代码
  • 任务拆分较多，适合子任务并行推进
  • 需要更强的过程控制，避免模型跑偏

openspec

openspec 更偏 spec-driven development，也就是“先写规范，再写实现”。它的核心目标是让人和 AI 先对齐要做什么，然后把这个对齐结果沉淀到仓库里，后续实现都围绕这些 spec 进行。

功能

  • 用 proposal、design、tasks 等文件组织一次变更
  • 将 specs/ 作为系统当前行为的事实来源
  • 将 changes/ 作为待实现变更的工作区
  • 支持从提案到实现，再到 archive 的完整闭环
  • 通过 spec delta 让人快速审查变更影响

使用方式

OpenSpec 的具体命令会随着接入方式略有差异，但整体流程通常是：

  1. 初始化项目
  2. 创建一个变更提案
  3. 进入规划或设计阶段
  4. 按 spec 实现代码
  5. 验证后归档

有些集成会提供类似 proposal、apply、archive 这样的命令入口。初始化后，项目里通常会生成 specs/、changes/ 和配置文件，方便后续持续维护。

适合场景

  • 大一点的功能开发，先统一规格再写代码
  • 需要长期维护的项目，希望把上下文留在仓库里
  • 变更较多，想用 spec 追踪历史和影响范围
  • 团队协作时，减少“我以为”和“你以为”的偏差

关系

  • superpowers 更像 workflow 的执行框架，强调怎么把任务稳稳做完
  • openspec 更像 workflow 的规格框架，强调先把需求说清楚
  • 两者都可以放进 harness 工程里，作为让 AI 可控、可验证、可复用的上层组件

区分

  • RAG：专注于生成内容的质量和准确性，通过检索外部信息来增强生成过程。主要用于问答和内容生成场景。
  • MCP：是一种通信协议，定义了模型与外部工具或上下文的交互方式。它是基础设施层，支持技能的执行。
  • Skill：是具体的功能实现，如一个代码编辑技能或搜索技能。技能依赖于协议如MCP来与模型交互，并可能使用RAG来检索信息。
